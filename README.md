# 农业监测 · GIS 可视化

一个**乡镇尺度**的农业监测看板：**地块、路网、设施是真的**（OpenStreetMap），
**监测值（气温/湿度/土壤水分/生长进度/病害扩散/水肥保持/耕作·休耕·收获·产量）由本项目模型生成**，
真实气象（NASA POWER）只当**校准锚点与验收基准**。纯静态、无构建、无后端、运行时零外部请求 ——
丢到 GitHub Pages 上就能跑。

演示区：**Hallertau · Wolnzach（德国巴伐利亚，世界最大啤酒花产区）**，15 km² 内的
**501 块地 / 990 ha**，549 天（2024-07-01 ~ 2025-12-31，含冬作物完整跨年生育期）。

> 前身是一个六边格贸易游戏。经济循环、商队、任务列表、道路铺设那一套**已全部作废**
> （它当初只是为了验证"道路与地点数据展示"），只保留了"路网 + 地点"作为监测数据的空间载体。

## 快速开始

```bash
npm run data:all        # 全流水线：取数（含行政边界/居民点/DEM/土壤）→ 可达性/经营单元/分区/情景 → 校验 → 导出 16 张表
                        #            → 透视查询（含与 DuckDB 的交叉验证，没装 DuckDB 会自动跳过）→ 仓库卫生
                        #   = parcels → roads → poi → weather → access → units → zones → check → export:tables
npm test                # 模型判据 40 条
npm run test:browser    # 真浏览器验收 205 条（Chrome/Edge，找不到浏览器时自动跳过）
npm run export:tables   # 单独重跑表格导出（含 31 条导出判据，失败即非 0 退出）
npm run export:daily    # 按需落盘"地块 × 日"长表（275,049 行 / 13.7 MB；默认不生成，另有 2 条判据）
npm run smoke:browser  # **页面冒烟**（约 7 秒）：页面能起来 + 加载期无异常 + 关键规模对得上
npm run ready          # **改完代码/页面先跑这一条**：模型冒烟 + 页面冒烟 + 查询 + 交叉验证 + 仓库卫生

npm run serve           # 启动静态服务器 → 打开 http://localhost:8080/
npm run serve:sub       # 同上，但挂在子路径下 → http://localhost:8080/webtrade/
npm run serve:lan       # 再打印局域网地址，手机同网段可直接打开（测窄屏）
```

⚠️ **必须走 http 服务**：`file://` 直接双击 `index.html` 会被浏览器的 ES 模块与 CORS 规则拦住
（模块脚本、`fetch('data/*.json')` 都不允许），页面会停在"页面初始化失败"。

`tools/serve.mjs` 是零依赖的 node 静态服务器（不用 python、不用 `npx serve`）：
`.geojson` 会给对 `application/json`、响应带 `no-store`（改完刷新即生效）、
并且支持 `--prefix` —— **子路径模式才是 GitHub Pages 项目站的真实形态**（`user.github.io/<repo>/`），
相对路径写错只有这样才能发现。

> Git Bash 用户在命令行直接传 `/webtrade` 会被 MSYS 改写成 `C:/Program Files/Git/webtrade`
> （Windows 路径转换）—— 所以 `serve:sub` 里写的是**不带前导斜杠**的 `--prefix webtrade`，
> 服务端两种写法都接受。手动跑就写 `--prefix webtrade`。

## 什么数据是真的，什么是模型生成的

| 层 | 来源 | 说明 |
|---|---|---|
| 地块几何 | **真实** | OSM `landuse=farmland/meadow/orchard/vineyard`，ODbL（署名即可商用） |
| 路网 | **真实** | OSM `highway=*`（含 `track` 田间道 —— 农机进出靠它） |
| 农业设施 | **真实** | OSM 的筒仓/谷仓/农机库/农资店。**OSM 是自愿标注，乡村覆盖不全，数量少是真实情况** |
| 气象 | **程序生成 + 实测校准** | 生成器只吃该站三个实测统计量（年均温、年振幅、雨日频率），季节相位/天气过程/日较差/辐射/湿度结构都得自己长出来；验收时与同期 NASA POWER 对比 |
| 作物 / 农事 / 产量 / 病害 / 水肥 | **模型生成** | 不是观测数据，不能当农情依据 |

`data/parcels.geojson` 里每块地都带 `crop_source: "simulated"`，界面的"说明"弹窗也如实写着这件事 ——
**不要把模拟值当观测值**是这类看板的第一条纪律。

## 模型口径（每条都能被数据打回）

1. **适种性由积温决定**。本区实测（NASA POWER，按各自生育期窗口算）：
   冬小麦 2615、冬油菜 1674、**青贮玉米 986**、啤酒花 1750 ℃·d；
   **粒用玉米需要 1400+ ⇒ 不适宜**，所以作物结构里根本没有它 ——
   与德国真实作物结构一致（青贮玉米 206 万 ha vs 粒用 42.9 万 ha）。
2. **积温按生育期窗口算**：冬小麦是"上年 10 月播 → 次年 7 月收"，拿全年 GDD 去比作物需求是量纲错误。
3. **收成/农事按季推进**：每季有自己的 `{播种日, 收获截止日}`；收获要么积温达标，要么到农事日历的硬日子
   （晚播青贮玉米不会等到霜前）；休耕地块没有播种与产量。
4. **病害是时空过程**：先按温湿算促病指数（**RH 低于阈值直接归零**），再按风向在邻域传播
   （用促病指数当源强，不是用等级 —— 等级从 1 起，用等级当源强会让健康地块天天"传染"）；
   约 55% 的地块有药剂防治，病情被封在 3 级以下。
5. **生长进度** = 积温累积 / 该作物需求；**水肥保持** = 根区湿度 × 地块土壤质量，与"基肥 − 吸收 − 淋失"。
6. **告警阈值按本地区分位数定**（水分 p15/p85、生长期气温 p2/p98、日降水 p97、病害 ≥3 级）。
   绝对阈值换个地区立刻失效：本区根区湿度只有 0.61~0.80、生长期日均温最高 25.7 ℃。

## 多维度数据模型（星型：dim_* 维度 · fact_* 事实 · meta_* 元数据）

**三条主线**（看一眼就知道怎么连表）：

```
空间：dim_admin ─→ dim_grid(P4 250m) ─→ dim_unit(P2 经营单元) ─→ dim_parcel(P1 田块)
时间：dim_date(日) ─┬─ fact_region_daily      区域×日（宽表）
                   ├─ fact_observation        区域×日×变量（长表，OGC 观测口径）
                   └─ fact_unit_decade        单元×旬×多变量（国内农业气象旬报：上旬/中旬/下旬）
变量：dim_variable（代码/单位/值域/告警规则/依据）⇒ 长表只需 variable_code 一列，**加变量不用改表**
事件：dim_parcel × dim_date → fact_parcel_event（播种/施肥/收获）
收成：dim_parcel × dim_crop × 作物年度 → fact_parcel_season（单产/总产/病害峰值，粒度放宽）
```

**字段口径对着国内权威规范落**（不是自己拍的）：

| 规范 | 落成什么 |
|---|---|
| **NY/T 4061-2021《农业大数据核心元数据》** | `meta_dataset` 按标识信息/数据特征/时空范围三组（带 M/O/C 必选标记） |
| **NY/T 4997-2025《农业资源数据元》** | `dim_data_element`：**每张表每一列一条数据元**（中文名/英文名/定义/数据类型/数据格式/值域/计量单位/来源） |
| **GB/T 19710 地理信息 元数据** | CRS / 空间分辨率 / 空间范围 |
| **《农村土地承包经营权要素编码规则》** | 编码结构 = **行政区划码 + 图层码 + 顺序号**（`09186-P-000001`；换到中国只换前缀，表结构不动） |
| **第三次全国土壤普查属性规范 + GB/T 33469 耕地质量等级** | `soil_texture/soil_ph/soil_organic_matter/land_quality_grade` 列位（**留空，不编造**） |
| **OGC SensorThings API** | 观测长表口径：`thing_id / spatial_level / spatial_id / variable_code / phenomenon_time / result_value / result_uom` |

**为什么"多维度"真的好用**：同一份数据可以是宽表（`fact_region_daily`，直接看）也可以是长表
（`fact_observation`/`fact_unit_decade`，直接透视），而 `dim_data_element` 保证**任何一列都能查到
它是什么、什么单位、值域多少、来自哪、是不是模拟值** —— 表能不能被人读懂，全靠这一张字典。

Excel 版在 `tables/农业监测数据.xlsx`：16 个工作表、冻结首行、自动筛选、列宽自适应。
透视示例：行放 `decade_key`、列放 `unit_id`、值放 `progress_mean`，就能看出各单元的进度差异。

## 透视与联合查询（先摆方案 → 查成熟做法 → 再定实现）

星型模型的代价是"事实表里只有键"：想读一眼就得先连维度；而"各单元逐旬进度""各网格各作物面积"这类问题，
本质是**透视**（行维 × 列维 × 度量 × 聚合）。这两件事以前只能靠人拿 Excel 手点，于是"数字怎么来的"说不清。

### 一、初始方案（5 个）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 自研零依赖引擎** | 自己写**星型连接 + 透视 + 多条件筛选**三个原语（纯 node） | 语义正确性要自己兜（靠判据 + 交叉验证） |
| B DuckDB | `read_csv_auto` 直接查 CSV，原生 `PIVOT … ON … USING` | 引入外部引擎（pip / CLI 安装） |
| C Python + pandas | `pd.pivot_table` / `merge` | 依赖 pandas；结果要落盘才能给 node 侧用 |
| D JS 内存 SQL 库（AlaSQL / sql.js / arquero） | node 里跑 SQL 或 dataframe 算子 | 打破"**零 npm 依赖**"（本项目 `dependencies` 为空是刻意的） |
| E BI 平台（Superset / Metabase） | 起服务、连数据源、拖拽 | 要后端与账号体系，与"纯静态交付"方向相反 |

### 二、查到的成熟做法（2026-10 检索）

- **DuckDB**（实测 1.5.6）：嵌入式 OLAP，可直接 `read_csv_auto('tables/*.csv')`，
  且**原生支持透视语句** `PIVOT tbl ON col USING AVG(x) GROUP BY rows`；MIT、单文件、Windows 可用 —— 被称为"分析界的 SQLite"；
- **pandas `pivot_table`**：算出的是**静态值**，写进 Excel 的不是活透视表；
- **Excel 真透视表**：查证的结论是**做不到** —— xlsxwriter 明确不支持写透视表，openpyxl 连读 `ws.pivot_tables` 都会报错；
  手写 `pivotCache/pivotTable` 那套 OOXML 风险高，而数据已经在整洁的 sheet 里，用户在 Excel 里点两下就能建
  ⇒ Excel 侧只给**透视视图**（静态 CSV + Markdown）；
- **JS 侧**：AlaSQL 支持 JOIN/GROUP BY 但要引依赖；Flexmonster 是商业件 ⇒ 与"零依赖、随仓库走"冲突。

### 三、结合本项目实际的选择

```
主实现 = A 自研零依赖引擎     ：dependencies 为空是刻意的；工具要能离线跑、随仓库走；每条语义都能被判据钉住
加强项 = B DuckDB（可选）      ：用成熟引擎做**独立实现的交叉验证**，补上"自研自己验自己"这个漏洞
不做   = C / D / E            ：引入依赖或后端，与纯静态交付冲突
不做   = Excel 真透视表        ：技术上不可行（已查证），且用户点两下就能建
```

关键点：**两套实现跑同一批 CSV、算同一批问题、逐格对比** —— 一致才说明"连接 / 透视 / 聚合 / 口径"的定义是清楚的。

### 四、落地结果（含本轮补齐的四件事）

**三个原语**（`tools/query.mjs`，纯 node、零依赖）：

| 原语 | 做什么 | 例子 |
|---|---|---|
| `joinStar` | 事实表 ⟕ 维度表，展开外键，**行数必须不变** | `fact_parcel_season` ⟕ `dim_crop` ⇒ 拿到单产口径 `yield_basis` |
| `pivot` | 行维 × 列维 × 度量 × 聚合（sum/mean/count/min/max），带行列合计与样本数 | 单元 × 旬 ⇒ 进度矩阵（62 × 54） |

**7 个预置查询**（每条都带业务问题，汇总在 `tables/query/透视与联合查询.md`）：
① 单产（行 = 作物 · 口径 × 列 = 年）② 单元 × 旬 进度矩阵 ③ 网格 × 作物 面积
④ **观测长表 → 宽表**（日期 × 变量）⑤ **多条件联合筛选** ⑥ **四层空间钻取链**（乡 → 县两级）
⑦ 管理分区 × 作物。

**五条"不许糊过去"的规矩**（全部做成判据）：① 连接不许膨胀行数；② 外键不许有孤儿；
③ **单产不许跨口径平均**（混口径的格子标 `*`，绝不静默出数）；④ 透视要守恒（单元格合计 == 原列合计）；
⑤ **空 ≠ 0**：求和时空值当 0（= SQL 的 SUM 忽略 NULL），**均值必须跳过空值**（= SQL 的 AVG 忽略 NULL），
而"全是空值"时合计要**保持空**而不是写 0（0 是"真·零收获"，空是"没有记录"）。
第 ⑤ 条是被交叉验证逼出来的：把比较函数的空值语义收紧后**第一次运行**就报出 4 处"自研 0 vs SQL null"。

**交叉验证**（`npm run query:sql`，DuckDB 1.5.6）：**8166 个格子逐格一致**（另含与原生 `PIVOT` 宽表对齐的 3348 格）、
联合筛选命中集合完全相同、分层去重计数一致。覆盖口径说清楚：`tables/` 下共 **6 张 `fact_*`**，
其中 fact_parcel_season（q1/q10）、fact_unit_decade（q2/q11）、fact_observation（q4）、fact_zone（q7）此前已覆盖，
本轮补上 **fact_region_daily（q8）与 fact_parcel_event（q9）**，并对前两张再做了"按年/按旬"的汇总口径对比。

> **失败与跳过是两件事**：环境没有 DuckDB ⇒ 打印提示并**跳过**（退出码 0，它是可选加强项）；
> 有 DuckDB 却把 SQL 跑挂了 ⇒ **真失败、退出码 1**（曾经写成"warn 一行 + exit 0"，等于把失败伪装成跳过）。

> 没有 DuckDB 的环境会**跳过**交叉验证（退出码 0）：它是加强项，不是交付前置条件 ——
> 交付物是 CSV / Excel / JSON，网页是纯静态的。

`layer.options = Util.extend({}, this.options.style)` —— 而我们的 `style` 是个**函数**，
于是"复原"后地块拿到的是**默认样式（Leaflet 默认蓝 + 粗线）**。现象就是用户报的
"点选表格高亮很多地块，但**无法取消**"：越点越蓝、且再也不会回到变量着色。
（同一个坑还在 `mouseout` 上：鼠标划过一块地就把它变成默认蓝且回不去。）
修法是**不复原、重算**：`restoreStyle(layer)` / `clearHighlight()` 都走自己的 `styleFor(feature)`，
与每帧刷新同一个来源。事件委托照旧挂在常驻容器上（表格每帧重写，绑在行上必然失效）。

阈值判定**复用告警那套分位数阈值**（`this.th`）—— 表里写的和告警里判的必须是同一套，
否则会出现"表说正常、告警说超标"这种最伤信任的错。

**导出**：`导出 CSV`（当前帧 501 个地块，列名与 `tables/fact_parcel_*` 对齐，便于与离线表对账）、
`导出 PNG`（把 Leaflet 的 canvas 层合成一张图，并画上标题/日期/图例，贴进汇报材料不用再解释；
**不含 `divIcon` 标签**，为守住"零依赖"没引 html2canvas）。

## 数据视图：右侧抽屉（全行 + 筛选 + 排序）

底部条是"扫一眼"的**预览**（720p 只有 132px，62 行的表只露 5 行）；要看全、要查、要排，走**数据抽屉**：

| 能力 | 说明 |
|---|---|
| 打开 | 顶栏「数据视图」或表格区「数据视图」（两个入口） |
| 内容 | 与底部条**同一批表**（7 个页签）、**全行**、列宽自适应 |
| 筛选 | 关键字（任一列包含即命中），标题里写"筛选后 N 行" |
| 排序 | 点任意列头：首次降序（这类表关心"最严重的那几块"）、再点升序、箭头提示方向 |
| 联动 | 点行 ⇒ 图上高亮该组地块；点告警里的地块 ⇒ 定位（与底部条同一条通道） |
| 导出 | 「**导出结果**」导的是**当前视图**（筛选 + 排序后的行，不是全表）；文件名带上日期与筛选口径，离开页面后还说得清口径 |
| 关闭 | **三个入口**：× / 点遮罩 / Esc（与帮助弹窗同一套习惯） |
| 打开时 | **自动暂停播放** —— 数字自己在跳的表格没法读 |

**为什么是"右侧抽屉"而不是全屏或顶部切页签**：这页最值钱的是**表↔图联动**。
全屏数据视图 / 顶栏切标签都会把联动切断（得来回切视图才知道"刚才高亮了哪几块"）；
抽屉只占右侧 **62%**，左侧地图仍可见且可交互（判据实测：抽屉宽 893px、**地图命中测试通过**），
点一行立刻能在图上看到高亮。窄屏（≤899px）时抽屉自动占满宽（再留 38% 地图就没法看了）。

底部条与抽屉共用同一份表格逻辑（`UI.buildTable(key)`）—— 七张表的取数分支只写一遍，
否则"底部条说 33 块、抽屉说 38 块"这种账对不上迟早发生。行内联动也共用同一套 `data-*` 属性。

**布局预算（都是量出来的，见下节）**：抽屉标题栏只放"标题 + 计数"（可截断），交互提示移到**页脚状态行**；
筛选框固定 ≥170px 不许被挤；排序列表头有**持久高亮**（不只靠 ▲▼），页脚写明"已按 XX 降序"。

**窄列宽（≤1240px）的取舍**：页签**不折行**（单行 + 横向滚动）、说明文案**收进抽屉**、STRIP 里的「导出 CSV」隐藏（抽屉里有同入口）。
理由：页签折行时表头能占 154px，而整个表格区只有 192px ⇒ 表体只剩 39px，等于把表格区废掉。
改完实测（1024×640）：**表头 154→63px、表体 39→130px**，从"看不到 1 行"变成"能看 3 行多"。

## 表格区为什么"只能这么大"（量出来的空间预算）

同一屏要分给顶栏 / 地图 / 表格区 / 底栏，**竖向是零和的**。实测（真浏览器、四种体型）：

| 体型 | 地图 | 表格区 | 表格区**可滚动高度** |
|---|---|---|---|
| 1440×900 | 559 px（62%） | 267 px（30%） | 201 px（62 行的表只看得到 **8 行**） |
| 1280×720 | 409 px（57%） | 216 px（30%） | **132 px**（只看得到 **5 行**） |
| 1024×640 | 336 px（53%） | 192 px（30%） | **60 px**（只看得到 **2 行**） |
| 390×844 | 388 px（46%） | 376 px（45%） | 整页滚动（可用，但不是看板体验） |

所以三条设计结论（都落了地）：

1. **页签不往下叠**：1024×640 下页签会折行，把可用行数压到 0~1 行 ⇒ 改成「只留前 3 个页签 + 「更多…」下拉」承载其余；
   表格本身按"结论/指标/空间/趋势/异常/方案/透视"划分，**透视视图**是第 7 张（矩阵由离线工具算好，页面只查表）；
2. **给一个"展开表格"开关**（表格区 30vh ⇄ 62vh，地图让位）：**读数据与看地图分时复用同一块屏幕**，而不是把表格叠得更高（实测 270→558 px，地图仍留 268 px，一键复位）；
3. **行数透明**：表头写"**共 N 行**"—— 132 px 里只露 5 行时，用户必须知道还有多少没看到。

**为什么不做页内"自由透视/查询构造器"**：① 政企看板的使用者要的是**答案**不是**分析台**（自由拖拽行/列/值对业务人员是门槛）；
② 地块×日有 **275,049 行**，实测对象数组 160 ms / 53 MB，列式量化 9 ms / 5.8 MB（堆外）—— 页内透视必须走列式 + 抽屉 + 冻结时点；
③ **已有 Excel 出口**：`tables/农业监测数据.xlsx`（13,336 行、冻结首行 + 筛选、含数据元字典）本来就能透视。
所以"联合查询"落地成**预设问题**（见上表最后一行），把自由探索留给 Excel。

## 情景推演：离线重算 + 浏览器查表

"新建一个收储点能带来多大改善"是一个**假设 → 重算全网最短路**的问题。
单个候选点跑一次单源 Dijkstra 是毫秒级，但把它搬进浏览器就得把 1500+ 条路、几千个节点和 Dijkstra
一起塞进页面，与"页面要轻"直接冲突。所以：

- `tools/scenario.mjs`：**离线**对 154 个候选点（350 m 网格）逐个重算全网时间 → `data/scenario.json`（140 KB）；
- 浏览器只做"**最近候选点查表**" + 高亮受影响地块 ⇒ 点下去是瞬时的。

结果（真实路网、真实地块）：现状平均 **4.62 分钟**、p90 7.68 分钟、盲区（> p90）**51 块 / 144.8 ha**；
最优候选点把平均降到 **3.32 分钟**、盲区降到 **2 块 / 16.8 ha**。

⚠️ 两条必须守住的语义（都有判据）：**新建一个点不可能让可达性变差** ⇒ 新建后取 `min(现状, 到新点)`；
盲区阈值是**现状 p90**（本地分位数，与等时圈层级同法），不是拍一个绝对分钟数。

## 三层空间单元（P1 自然田块 / P2 经营单元 / P4 统计网格）

参照欧盟 **LPIS** 把"稳定身份"与"逐年属性"分开的做法（`agricultural parcel` = 单一作物+单一农户的连续地块，
见 [FIG 2007](https://www.fig.net/pub/fig2007/papers/ts_1g/ts01g_03_inan_cete_1404.pdf)；LPIS 对外发布还有**匿名化**版本）：

| 层 | 是什么 | 本区结果 | 用途 |
|---|---|---|---|
| **P1 自然田块** | OSM 真实可见田块边界（`data/parcels.geojson`） | **501 块** / 990 ha / 中位 1.12 ha | 逐块作业与监测 |
| **P2 经营单元** | **空间连片的作业片区**（地块间距 ≤30 m、面积上限 30 ha，贪心合并） | **62 个** / 面积中位 19.7 ha / 最大 30 ha | 轮作计划、作业编组、管理口径 |
| **P4 统计网格** | 250 m 规则网格（按经纬度取整编码，可复现；思路同 OGC API – DGGS） | **217 格** | 汇总上报 |
| P3 管理分区（**演示**） | 25 m 网格采样 + 一维 k-means 分 2~3 区（方法同精准农业的 management zone）；`data/zones.geojson` 2.4 MB ⇒ **按需加载**（打开图层才拉） | 363 块地 / **12833 样点** / 744 区 | 变量施肥/灌溉的处方图雏形 |

两条被数据打回来的设计决定（都写进注释了）：

1. **"经营单元"不能要求同作物**。本区地块确实是连片马赛克（456/501 的最近邻 ≤5 m、中位距离 0 m），
   但**同作物相邻极少** —— 作物是逐地块抽的，任意相邻对同作物的概率只有 ~1/7；
   拿它当约束，501 块只能合出 351 个单元（等于没聚合）。语义上也该如此：**单元是空间单元，作物是属性**。
2. **邻接必须按"点到线段"算**。第一版用"顶点到顶点"，把真实相邻判成几十米远（T 型接头 + 抽稀后顶点稀疏），
   相邻候选对从上千对掉到 199 对。

## 可达性分析（算出来的，不是摆上去的）

路网早就有（1576 条路段，含田间道），但之前只是**背景画线**。`tools/build-access.mjs` 让它回答农业物流里
最实际的问题：**这块地到最近的收储点要走多久、谁的田头够不着？**

- 图：OSM 路段折点做节点、haversine 边长、按 `highway` 等级给速度（motorway 80 → track 12 km/h）；
- 源：OSM 的 `silo / barn / agrarian / marketplace` 共 **15 个**；
- **多源 Dijkstra** 一次算出"到任意收储点"的最短时间；再按 10 km/h 补一段"地块质心 → 路网"的接驳；
- 等时圈：规则网格上的时间场 + marching squares 抽等值线。

本区结果：**中位 4.4 分钟、p90 7.7 分钟、最远 11.8 分钟，0 块不可达**；
"下道距离" p90 = **433 m**（这才是真正的盲区信号：离路网越远，农机下道成本越高）；
等时圈层级 **3 / 4.5 / 6 / 7.5 分钟**（按 p25/p50/p75/p90 定 —— 写死 15/20 分钟在"全程 ≤13 分钟"的乡镇上
会是空图层）。

⚠️ 三个如实声明的局限：接驳段是直线（不是田间实际路径）、速度是等级经验值（不是限速）、
栅格分辨率 56×56。所以**只看相对格局，不要当成精确行程时间**。

## 纯静态保证（无后端 / 无 CDN / 任意静态服务器）

网页是**纯静态**的：只有 HTML/CSS/JS 与 `data/` 下的本地 JSON/GeoJSON，Leaflet 已本地化到 `vendor/`，
没有后端、没有数据库、没有 CDN、没有构建步骤。工具链里现在有了 node / python / DuckDB，
所以必须把界限写死：**离线工具怎么长大，都不许把依赖带进页面**。

5 条判据（`npm run test:browser` 第 21 节）把这条硬线钉住：

1. 运行期**只加载同源静态资源**（枚举 `performance` 里的请求：无外部域名、无 websocket、无后端接口）；
2. 页面源码**零外部依赖**（扫 `<script src>` / `<link href>` / `import … from` 无外链；源码里不出现
   `child_process` / `require(` / `duckdb` / `WebSocket(` / `/api/`）；
3. 换成**任意静态服务器**也能跑：判据里真的起了一个 `python -m http.server`（不含任何后端），导航过去验证
   （实测 501 个地块、地图容器就绪、无失败提示）；
4. 数据缺失时给**可读提示**（含补救步骤），而不是白屏；
5. **`file://` 直接打开也不白屏**：这种打开方式浏览器会拦掉 `type="module"` 脚本，连 `main.js` 里的 `fatal()`
   都不会执行 ⇒ 页面加了一段**内联**兜底（3 秒后仍无启动标记就把原因与做法写在页面上）。判据真的用 `file://` 打开过一次。

> 注：`file://` 下模块脚本与本地 `fetch` 会被浏览器的 CORS 规则拦掉，**正确用法是任意静态服务器**
> （`npm run serve`、`python -m http.server`、Nginx、对象存储、GitHub Pages 都可以）。
> 第 5 条保证的是"就算你这么打开了，也看得懂为什么"。

### 透视/查询与纯静态这一轮抓到的真 bug

- **`dim_crop` 的 `ORCHARD` 重复**（手写补行时没注意它已在 `CROPS` 里）⇒ 作物字典 9 行只有 8 个唯一码。

  ⇒ 改成**逐类显式映射**（缺映射就是空值，判据直接报）；

  node 按 UTF-8 解码 ⇒ 只含 ASCII 键的对比全通过、含中文列名的整片不匹配。改成**结果写显式 UTF-8 文件**、stdout 只回 ASCII；

  ⇒ 改成用**粗维度**（年 × 季序）反向验证"机制真的会拦"，否则这条判据只是在撞运气；
- **运距告警阈值定在数据之外**：`dim_variable` 里 `T_MIN_STORE` 的告警是 "> 12 min"，而本演示区运距**最大只有 11.8 分**

### 上一轮（页面冒烟 + ready）抓到的真 bug / 教训

- **`ready` 看不见"页面起不来"**：它只跑 query / query:sql / repo:check，

  并把"`ready` 里必须含它"做成仓库卫生判据（谁拿掉谁红）；

  并直接打出 `TypeError: UI.loadColHidden is not a function`（7 秒内）；改回来 ⇒ 5/0。
  "判据要能红"这件事不能靠推理，要靠注入一次故障看它真的红；

  改代码的实验里，**替换/注入都要断言命中数**。

### 上一轮（时序回放）抓到的真 bug / 教训

- **回放时"把未来也画出来"**：地图停在某一天，折线却把整个窗口摊开 ⇒ 两边说的不是同一件事。

  判据还因此抓到"画布引用失效"（拿到的是刚被丢掉的那张）⇒ 拆成"结构重建"与"只重画"两步，

## 图表规范：先检索成熟做法，再逐条落到判据

做"常用数据图示"这一轮时，先把**主流规矩查清楚**，再决定本项目怎么做（不凭个人偏好）：

| 查到的规矩 | 出处（检索所得） | 本项目怎么落 |
|---|---|---|
| **柱状图必须 0 基**（柱子用"长度"编码，截轴就是骗人）；**折线可以不满基**（用"位置/斜率"编码） | callingbullshit.org 的 misleading axes、storytellingwithdata 的"bar charts must have zero baseline"、Vizzlo 制图指南 | 柱状：0 基 + **柱顶标数值**（不靠截轴也能读）；折线：默认按数据范围铺满，**非零基时在图上写出**「轴 x~y（非零基）」角标 |
| 各图**自适应纵轴**最适合"看形状"；**共用纵轴**适合"比绝对量" | Flourish 的 line/bar 指南 | 折线带**序列开关**：四条合看 = 共用轴（比绝对量）；只看一条 = 收到它自己的范围（看形状）。实测对比度 **19% → 89%（4.64 倍）** |
| 饼图：**小项合并为「其他」** + 直接标数值 + 从大到小排 | ClicData（"group minor categories into an Other slice"）、Chartio 的默认行为 | 作物 7 类 → 前 5 类单列 + 「其他（2 类）3.5%」；**合计守恒**（合并只改显示分组，不改数值，有判据） |
| **色盲安全配色**（Okabe-Ito）+ 颜色只作冗余编码 | Nature "Data visualization with flying colors"、R 的 ggokabeito、期刊制图规范 | 分类色统一走 `theme.js` 的 `PALETTE`（原折线用的红绿对是红绿色盲最难分的组合）；图注写明"别只靠颜色读，标签与百分比才是主读法" |
| 雷达图**不能拿多边形面积当综合得分**（轴的顺序一变面积就变）；维度要少 | 针对"用雷达图面积构造复合指标"的学术质疑（Pereira et al.）、AntV 雷达图指南 | 保留 5 维（并写明"维度再多就该换图"）；图注明确"只看形状与各维位置，**不要拿面积当总分**" |

| （同上）**差距太小的维度不许归一**，否则把噪声放大成整根轴 | 实测：养分保持全场只差 **0.04** | 归一前设最小跨度 0.05，低于它按"无区分度"画在中线；**阈值与图注统计共用同一个数**（两处各写一个必然对不上） |

| **图表"说明与事实一致"** | 四张图的标题与所画指标必须一致（③ 画的是**到收储点最远**，标题就不能写"面积"）；③ 的 12 个值 == 当日单元按 tMin 降序前 12（独立复算）；② 饼合计 == 当日作物面积合计；① 竖线位置 == 当前日期在抽样序列上的下标；并把"哪些图随日期变"**量出来**（雷达变 · 饼/柱不变，且"不变"是对的） | 5 条 |
| **时序回放：曲线裁到当前帧** | 折线与小曲线都只把"已经发生"的部分**画实**，之后画淡；纵轴仍按**全窗口**算（逐帧不跳，否则回放时图会抖）。判据量的是**实画像素的右边界**（只认序列配色的像素）—— 实测 `102px（20%）→ 322px（90%）→ 350px（末帧）`，这就是"画到哪儿"的精确证据；另加"纵轴范围三次调用完全相同" | 4 条 |
| **图表导出 PNG（两处）** | 图表页签「导出图表」把四张 canvas 拼成一张；抽屉里那张**上下文图**（排行 / 情景前后对照 / 农事日历堆叠柱）右上角也有「导出图」。两张都带**标题条（图种 + 口径 + 日期）**，走与「导出地图」同一条下载通道；都抽成纯函数（`chartPanelPng()` / `dwChartPng()`）便于判据 | 图表页签：dataURL 是真 PNG、按钮把 dataURL 交给下载通道；抽屉：**三类图各自**能导、文件名按图种区分（排行图/农事日历/情景前后对照） |

这一节的判据（§33 显示范围 / §34 图示规范 / §35 三件交互，共 13 条）钉住的就是上表：
折线只看一条时纵轴确实收紧且**跨 0 的序列仍保持 0 基**（不许假装收紧）、非零基**图角必须写出**、
柱状 0 基且柱顶有数值、雷达有区分度的维度用满 0~1 而**小差距维度不放大**、
配色是 Okabe-Ito 四色、饼图合并且合计守恒、两条口径说明互相不矛盾。

## 有意**不做**的两件事（说清理由，不是漏了）

1. **不做"县级/乡级聚合着色"**：`data/admin.json` 存的是**行政界线**（OSM boundary way 原样保留，不缝合多边形），
   本项目刻意**不渲染行政区域面** —— 填色等于绘制行政区域，会牵扯审图号那套合规问题（见 `js/map.js` 的注释）。
   要看聚合，用 P2 单元 / P4 网格（都是本项目自己的统计单元，不涉合规）。
2. **不把 `npm run ready` 挂进 `data:all`**：`data:all` 末尾**已经**依次跑了 `query` → `query:sql` → `repo:check`（另补了模型冒烟），
   再挂 `ready` 就是同一件事跑两遍。`ready` 的定位是"**只改了代码/页面**、不想重跑取数时的一条命令"。

## 已知限制 / 下一步

- **`fact_parcel_daily`（地块 × 日，275,049 行 / 13.7 MB）默认不在仓库里**：它完全由确定性模型重算得出，
  用 `npm run export:daily` 按需生成（已加进 `.gitignore`）。要交付给外部系统时跑一次即可，附带 2 条判据。

- **Leaflet 默认标注/图层控件的图标没有本地化**：`vendor/leaflet/leaflet.css` 里那三处
  `url(images/…)` 已**删除**（改成说明性注释）—— 本项目只用 `circleMarker` / `divIcon`，不触发这些路径。
  若以后要用默认标注，把官方 `dist/images/` 的图片补进 `vendor/leaflet/images/` 并恢复那几行即可。
  这条现在由 `npm run repo:check` 的「**CSS 里引用的本地文件都存在**」判据守住（再写死引用会直接红）。

- **气温是区域量**，不做地块级着色：OSM 不提供每块地的高程，硬编一个地块级温度场就是造假。
  将来接入 DEM（如 Copernicus GLO-30）后可以按高程递减率做出真实的空间差异。
- **产量/病害没有实测对照**：目前只能用公开统计（单产区间）与农学阈值（温湿—促病）做间接校验。
  要更进一步，需要接入真实产量统计（USDA NASS / Eurostat / 县级统计年鉴）或遥感（Sentinel-2 NDVI）。
- 可达性用的是**等级经验速度 + 直线接驳**；要更准需要真实限速/路面数据，或上 Valhalla/OSRM
  （本乡镇规模自建 Dijkstra 已经够，不必引外部服务）。
- 等时圈目前是**等值线**（不是填充面片）；要填充需要把 marching squares 的输出接成多边形。
- 演示区可换：改 `tools/fetch-data.mjs` 的 `--bbox` 与 `--lat/--lon` 即可（任何 OSM 覆盖良好的乡镇）。
- 仓库**还没有 git**（`git init` 之后建议把 `data/` 与 `vendor/` 一起提交，它们是可复现的取数产物）。
